# Architecture Decision Records

## 철학
MVP 속도 최우선. 백엔드/외부 의존성 없이 정적 데이터로 작동하는 최소 구현을 선택하고, 콘텐츠는 팀원이 독립적으로 추가할 수 있게 플러그인 구조로 분리한다.

---

### ADR-001: Next.js App Router + TypeScript + Tailwind CSS 채택
**결정**: 프레임워크는 Next.js(App Router), 언어는 TypeScript strict mode, 스타일링은 Tailwind CSS.
**이유**: 기존 스캐폴드의 훅 설정(`tdd-guard.sh`의 Next.js 파일 예외, Stop 훅의 `npm run lint/build/test`)과 문서 템플릿이 이미 이 조합을 전제하고 있었음.
**트레이드오프**: 없음 (그린필드 프로젝트).

### ADR-002: 완전 정적 데이터, 백엔드/DB 미사용
**결정**: 회원가입/로그인/서버 저장 없이, 모든 콘텐츠(시나리오·사례·매물·대응방안)를 `src/data/`의 정적 TS 파일로 관리한다.
**이유**: MVP 속도, 인프라 설정 비용 제거.
**트레이드오프**: 기기 간 결과 공유 불가. 참고 리포 `detect-voicephsing`처럼 LLM이 매 턴 자유 응답을 실시간 평가하는 방식은 채택하지 않고, 보이스피싱 유형은 선택지 기반 분기 대화로 단순화한다. 백엔드가 없어 정답 데이터가 클라이언트 번들에 그대로 포함된다(devtools로 사전 열람 가능) — 경쟁·리더보드 요소가 없는 교육용 MVP라 고치지 않고 받아들이는 리스크로 채택.

### ADR-003: 세션 상태는 React Context만 사용, localStorage 없음
**결정**: 체험 진행 상태(순서, 선택, 결과)는 `SessionProvider`(React Context)에만 보관한다.
**이유**: "새로고침·이탈 시 매번 처음부터 재시작"이 제품 결정이므로 영속화 계층 자체가 불필요.
**트레이드오프**: 브라우저 탭을 닫으면 진행 중이던 세션은 복구 불가 (의도된 동작).

### ADR-004: 유형은 레지스트리 기반 플러그인 패턴, 사전 비공개 + 매 세션 랜덤 순서/콘텐츠
**결정**: 3개 체험 유형(보이스피싱/사례선택/전세매물)은 `ExperienceModule` 공통 인터페이스를 구현해 `lib/registry.ts`에 등록한다. 사용자에게는 유형 목록을 사전에 노출하지 않고, 매 세션 유형 순서와 유형별 콘텐츠를 랜덤 선택한다.
**이유**: 콘텐츠가 확정 전이라 팀원별 독립 추가/수정이 필요하고, "몰래 체험"으로 즉각적 판단력을 테스트한다는 제품 컨셉상 사전 메뉴 노출이 목적에 반함.
**트레이드오프**: 홈 화면에 유형별 진입 메뉴/딥링크를 둘 수 없음 — 랜딩은 하나의 "시작하기" CTA만 가진다.

### ADR-005: 모든 체험 콘텐츠는 피해자 관점(방어)만 다룬다
**결정**: 보이스피싱을 포함한 모든 체험 콘텐츠는 사용자가 사기를 "당할 뻔한" 피해자 시점으로만 작성한다. 참고 리포 `detect-voicephsing`에 있던 "Attacker Mode"(가해자 관점 체험) 같은 콘텐츠는 만들지 않는다.
**이유**: 실제로 통할 수 있는 사기 대화 스크립트로 오용될 수 있는 콘텐츠 생성을 원천 차단하기 위함 (보안/콘텐츠 안전).
**트레이드오프**: 참고 리포에 있던 "가해자 관점에서 배우는" 몰입감·학습 효과는 포기한다.

### ADR-006: 보이스피싱만 채팅형 UI로 전환, 나머지 유형은 기존 "다음" 버튼 유지
**결정**: 보이스피싱 체험은 참고 리포 [javiow/sache](https://github.com/javiow/sache)의 채팅 UX
패턴(타이핑 인디케이터 + 메시지별 딜레이, 선택지 클릭 즉시 진행, 별도 전송/다음 버튼 없음)을
이식해 가해자-피해자가 실제 채팅하듯 대화가 이어지도록 재설계한다. 사례선택/전세매물은 기존
"선택 후 다음 버튼 클릭" 방식을 그대로 유지한다.
**이유**: 보이스피싱은 실시간 통화 상황을 다루므로 채팅형 UI가 몰입감·긴장감을 훨씬 잘
전달한다. 사례선택/전세매물은 두 대상을 나란히 비교하는 단발성 A/B 선택이라 채팅형으로 바꿀
이유가 없다.
**트레이드오프**: 3개 체험 유형의 인터랙션 패턴이 통일되지 않는다 — 다만 유형을 사전에
노출하지 않는 제품 특성상 사용자가 이 비일관성을 직접 비교해 체감할 일은 없다.
`ExperienceModule`/`ExperienceComponentProps` 계약(`content` prop, 단일 `onComplete` 호출)은
그대로 유지되므로 오케스트레이션 코드에는 영향 없다.

### ADR-007: 전세매물 유형을 팀원 제작 "골목 이동 O/X 판정" 게임으로 교체
**결정**: 기존 2択 카드 선택형 전세매물 체험을 팀원 레포([HousingFraudDetect](https://github.com/JUNGMyeong-jin96/HousingFraudDetect))에서 이식한 게임으로 완전히 교체한다. 사용자는 골목 맵을 걸어다니며 매물 5채에 들어가 등기부·전세가율 등 8개 서류 항목을 확인하고 위험 여부를 O/X로 판정한다. 캐릭터/건물 스프라이트는 canvas 절차적 픽셀아트로, 외부 이미지·라이브러리 의존성이 없어 이식 비용이 낮다. `ExperienceModule<JeonseHouse[]>` 계약(하나의 `content`를 받아 `onComplete`로 `ModuleResult` 1건 반환)은 그대로 유지하고, 5채 판정을 하나의 `ModuleResult`로 집계한다(`score = 정답수/5*100`, 등급이 "safe"(80%↑)일 때만 `isCorrect: true`).
**이유**: 팀원이 이미 검증한 콘텐츠(매물 42개)와 게임플레이를 그대로 활용하고, 다른 두 유형 대비 몰입감 있는 체험을 제공한다.
**트레이드오프**: 원작의 "판정 직후 정답 공개" UX는 제거한다(이 앱의 "결과 페이지에서만 공개" 원칙 위반이므로) — 학습 임팩트는 다소 줄되 세 유형 전체의 일관성을 우선한다. 이동/스프라이트가 추가되며 세 체험 유형 간 인터랙션 복잡도 격차가 커진다(ADR-006에서 이미 허용한 비일관성의 연장). 세션당 판정 항목이 1개→5개로 늘어 이 유형만 완료 시간이 눈에 띄게 길어진다.

### ADR-008: 캐릭터 설정(나이대/직업/성별)을 랜딩 이후 전역 1회 단계로 추가
**결정**: `/` 랜딩과 `/session` 사이에 `/setup` 단계를 신설해 나이대·직업·성별을 한 번 수집하고 `SessionProvider`의 `playerInfo`에 저장한다. 화면에는 노출하지 않고 향후 시나리오 매칭(콘텐츠 추천/난이도 조정 등)에 쓸 목적으로 보관만 한다 — 매칭 로직 자체는 이번 범위 밖. "다시 체험하기" 재시작은 `/setup`을 다시 거치지 않는다(`resetSession()`이 `playerInfo`는 건드리지 않음).
**이유**: 팀원 게임의 캐릭터 생성 단계를 버리지 않고 전역 자산으로 승격해 향후 개인화 기능의 기반을 마련한다.
**트레이드오프**: 랜딩→세션 사이에 화면이 하나 늘어난다. 지금은 수집한 정보를 아무 데도 쓰지 않는다(향후 매칭 기능 전까지는 순수 수집 단계).

### ADR-009: 팀원 제작 사기 판별 퀴즈(fraudtest)를 4번째 체험 유형으로 흡수
**결정**: 팀원 레포([KKanghh/fraudtest](https://github.com/KKanghh/fraudtest))의 사기 판별 퀴즈 콘텐츠 풀(15개 사기 유형 · 74개 시나리오 카드, 각 항목은 서술형 지문 1개 + 정답(fraud/safe) + 해설 + 출처로 구성)을 새로운 4번째 체험 유형(`typeId: "fraud-judgment"`)으로 흡수한다. 기존 3개 유형(보이스피싱/사례선택/전세매물)에 억지로 끼워 넣지 않는다 — 전세사기 6종은 구조화된 필드가 없는 서술형 지문이라 `jeonse`(서류 8항목 판정)에 맞지 않고, 지인사칭·몸캠피싱·택배기사 사칭 항목은 다중 턴 분기가 아닌 단일 서술형 문단이라 `voice-phishing`의 `DialogueNode` 트리에 맞지 않는다. UI는 팀원 원작의 "카드 1장 + 사기/정상 판정" 단일 카드 인터랙션을 그대로 따르되(카드 2장 비교형인 `case-select`와는 다름), 판정 직후 정답/해설을 공개하지 않는 이 앱의 원칙은 그대로 적용한다.
**이유**: 팀원이 이미 리서치·검증한 콘텐츠(15개 실제 사기 유형, 공식 기관 출처)를 커스텀 매핑 없이 그대로 재사용하고, 단일 카드 판정이라는 원작 UX를 최소 변형으로 이식할 수 있다.
**트레이드오프**: 4개 체험 유형 간 인터랙션 패턴 이질성이 한 단계 더 커진다(ADR-006/007에서 이미 허용한 비일관성의 연장, 유형 비노출 제품 특성상 사용자가 직접 비교 체감할 일은 없음). `source` 필드가 정답을 암시하는 값(금융감독원/경찰청 등 사기예방기관명)을 담고 있어, `explanation`과 마찬가지로 체험 중에는 절대 노출하지 않고 `/result`에서만(설명 문구에 결합해) 노출하도록 별도 처리했다.

### ADR-010: "사례 선택"을 팀원 제작 부동산 사기 조사 게임(red-flag)의 6개 케이스로 교체
**결정**: 기존 2択 카드 비교형 "사례 선택"(`typeId: "case-select"`) 체험을 팀원 레포([dakyommii/red-flag](https://github.com/dakyommii/red-flag))의 부동산 사기 추리 게임에서 이식한 콘텐츠로 완전히 교체한다(`typeId: "case-investigation"`). 원작은 FastAPI 백엔드 + LLM 기반 NPC 자유대화가 있는 풀스택 앱(전세 3종·청약 1종·분양 1종·복합 파이널 1종, 총 6개 케이스)이지만, 이 프로젝트는 백엔드/LLM 호출이 전면 금지이므로 다음과 같이 단순화해 이식한다: (1) 채점(`scoring.py`)은 이미 순수 rule-based(LLM 미사용)라 그대로 TS로 재구현한다(위험신호 발견 40 + 증거 품질 20 + 모순 15 + 조사 효율 10 + 최종판단 점수, 합을 0~100으로 clamp). (2) NPC 자유대화는 케이스별 고정 질문 버튼(원작 `suggested_questions` 중 대사와 매칭되는 것만 채택) → 클릭 시 고정 대사 노출로 대체한다. (3) 조사 포인트/비용 시스템(문서마다 비용 소모, 일부는 다른 조사 완료·증거 등록이 언락 조건)은 그대로 유지한다. (4) 원작의 드래그 연결형 모순 발견 UI는 만들지 않고, "관련 질문을 클릭 + 관련 증거를 등록"하면 자동으로 모순 점수를 획득하는 방식으로 단순화한다. (5) 최종 판단은 원작 그대로 3지선다(계약 진행 가능/추가 확인 필요/계약 중단)를 유지한다 — 케이스별로 최고점 선택지가 다르다. (6) 시간제한(`time_limit_seconds`) 카운트다운은 구현하지 않는다 — ADR-003 원칙과 맞고, 시나리오 텍스트로만 서사적으로 유지한다.
**이유**: 팀원이 이미 리서치·검증한 콘텐츠(실제 전세사기·청약사기·분양사기 사례 기반 6개 케이스)를 활용하면서, "정답은 LLM이 아니라 rule-based로 결정한다"는 원작의 설계 철학이 이 프로젝트의 백엔드 미사용 원칙(ADR-002)과 자연히 맞아떨어진다.
**트레이드오프**: 원작의 LLM 자유대화·모순 연결 UI·타이머 긴장감은 포기한다. 4개 체험 유형 중 상태가 가장 복잡한 유형이 된다(포인트·언락·증거등록·NPC 대화·3지선다를 한 컴포넌트가 관리) — 다만 영속화 계층 없이 단일 컴포넌트의 `useState`로만 구성해 ADR-003 원칙은 그대로 지킨다.

### ADR-011: fraudtest 콘텐츠 재동기화 (15→19개 유형, 74→90개 카드)
**결정**: ADR-009 이후 팀원 레포 fraudtest에 추가된 신규 유형 4종(가상자산_사기·파밍_사기·보험사기·명의도용_사기, 각 fraud/safe 미니멀 페어 2쌍씩 총 16개 카드)을 `src/data/fraud-judgment.ts`에 추가 포팅하고, 기존 카드 중 fraudtest에서 내용이 개정된 1건(`lease-trust-safe` — "동의서를 받았다"에서 "신탁회사 대표번호를 직접 검색해 전화로 재확인했다"는 독립 검증 서술로 개정)을 최신본으로 교체한다. `FraudJudgmentCategory` 유니온과 관련 테스트도 19개 유형 기준으로 함께 갱신한다.
**이유**: ADR-009는 한 시점의 스냅샷 포팅이었고 fraudtest와 런타임 연동은 두지 않는다는 원칙(ADR-002)은 유지하되, 팀원이 추가로 리서치·검증한 콘텐츠를 반영해 커버리지를 넓힌다.
**트레이드오프**: 여전히 수동 재동기화이므로 fraudtest가 다시 갱신되면 또 수작업 포팅이 필요하다 — 자동 동기화 파이프라인은 만들지 않는다(백엔드/외부 의존성 없음 원칙, ADR-002).

### ADR-012: 난이도 선택 단계를 `/setup`과 `/session` 사이에 추가
**결정**: `/setup`(캐릭터 설정)과 `/session` 사이에 `/difficulty` 단계를 신설한다. 사용자는 쉬움/중간/어려움 중 하나를 선택하고(각 난이도에 한 줄 설명), 선택값은 `SessionProvider`의 `difficulty: Difficulty | null` 필드에 저장된다. `ExperienceModule.pickRandomContent(difficulty?)`가 이 값을 받아 해당 유형의 콘텐츠 풀을 그 난이도로 좁힌 뒤 랜덤 선택한다. 난이도 태그가 없거나 해당 난이도 항목이 없는 풀은 전체 풀에서 그대로 랜덤한다(fallback). 이번 범위에서 난이도 태그가 실제로 존재하는 유형은 전세매물(`JeonseHouse.difficulty`, 42채 전부)뿐이며, 나머지 3개 유형(보이스피싱/케이스 조사/사기 판별 카드)에는 `difficulty` 필드를 선택적(optional)으로만 추가하고 콘텐츠 태깅은 후속 작업으로 미룬다. 전세매물은 콘텐츠 단위가 "매물 5채 세트"이므로, 난이도가 주어지면 `JEONSE_HOUSES`에서 해당 난이도 매물만 필터링해 랜덤 5채로 세트를 즉석 구성한다(해당 난이도 매물이 5채 미만이면 기존 `JEONSE_HOUSE_SETS`로 fallback). "다시 체험하기" 재시작은 `/difficulty`를 다시 거치지 않는다(`resetSession()`이 `difficulty`를 건드리지 않음 — ADR-008의 `playerInfo`와 동일 규칙).
**이유**: 난이도별로 체험 강도를 조절하고 싶다는 팀 요구를 충족하되, 콘텐츠 난이도 판정(특히 실제로 통할 수 있는 사기 시나리오)은 도메인 판단이 필요한 팀원 몫이므로 메커니즘만 먼저 넣고 태깅은 분리한다. 전세매물은 이미 팀원이 42채 전부에 난이도를 매겨 뒀으므로(`f02673f`) 즉시 활용 가능하다.
**트레이드오프**: 랜딩→세션 사이 화면이 하나 더 늘어난다(`/` → `/setup` → `/difficulty` → `/session`). 4개 유형 중 3개는 콘텐츠가 태깅될 때까지 난이도 선택이 실질적으로 효과가 없다(전체 풀 랜덤으로 fallback) — 사용자에게는 난이도가 반영되는 것처럼 보이지만 실제로는 전세매물만 달라진다. `difficulty`는 Context에만 살아 새로고침 시 소실된다(나머지 세션 상태와 동일, ADR-003). 전세매물 난이도 필터는 기존 큐레이션 세트(`JEONSE_HOUSE_SETS`) 대신 즉석 5채 추출을 쓰므로 세트 내 위험/안전 매물 균형은 보장하지 않는다(기존 세트도 균형이 보장돼 있지 않았음). 즉석 추출로 인해 그동안 어느 세트에도 안 들어가던 매물(현재 인덱스 40·41, id "41"·"42")이 노출되기 시작한다.

### ADR-013: 랜딩을 풀 히어로로 개편하고 마스코트를 표정 프레임 기반 인터랙티브 컴포넌트로 교체
**결정**:
- 랜딩(`/`)을 "정적 이미지 1장 + 헤드라인 + 진행 방식 카드 + CTA"의 세로 정렬에서, 화면을 꽉 채우는(`min-h-screen`) 히어로로 재구성한다. 히어로 중앙에 애니메이션 마스코트를 두고, 주변에 장식용 "가짜 스캠 알림" 카드가 떠다니며, 배경은 크림 톤 그라디언트 + CSS 그레인이 은은히 움직이고, CTA에 pulse를 준다. "진행 방식" 안내 카드는 스크롤 아래 `#how-it-works` 섹션으로 내리되 문구는 그대로 둔다.
- 마스코트를 팀 제공 픽셀아트 코끼리 표정 6종(`idle`/`blink`/`surprised`/`worried`/`sleepy`/`sad`)으로 교체한다. 소스 8장은 배경 불투명·중복 2쌍이라, 1회성 로컬 스크립트(Python PIL, **앱 코드로 커밋하지 않음**)로 모서리 flood-fill 투명화 + 트림 + 정사각 패딩 + 512px WebP 변환해 `public/mascot/`에 6개 프레임으로 넣는다.
- `Mascot` 컴포넌트를 레이어드 `next/image` 프레임 + opacity 크로스페이드로 재작성한다. `className?`만 받던 것에 `expression?`(제어) / `interactive?`(idle 루프 + 포인터·hover·포커스 반응) / `proximityRef?` 등을 **선택적으로만** 추가하고, props 없이·`SessionProvider` 없이 장식용 `img`(`aria-hidden`)로 렌더되는 기존 계약(`Mascot.test.tsx`)은 유지한다.
- 마스코트 모션 상태 머신은 순수 로직 훅으로 분리한다 — `src/lib/mascot-frames.ts`(표정→이미지·등급→표정 매핑 + 타이밍 상수), `src/lib/useReducedMotion.ts`, `src/lib/useMascotExpression.ts`(idle 깜빡임 루프 + 커서 근접 시 "놀람→걱정→복귀" 트리거). 새 npm 의존성은 추가하지 않고 애니메이션은 `globals.css`의 `@keyframes`로만 구현한다.
- `/result` 종합 정답률 섹션에 등급별 정적 마스코트를 추가한다 — `safe`→`relieved`, `caution`→`worried`, `danger`→`sad`. 제어 모드라 idle 루프·포인터 반응 없음.
- 랜딩을 서버 컴포넌트로 유지하기 위해 인터랙티브 히어로는 `src/components/ui/LandingHero.tsx`(`"use client"`) 아일랜드로 분리하고, `page.tsx`는 `<LandingHero />` + `#how-it-works` 섹션만 조립한다.
- 한글 서비스명(헤드라인)을 속담 "눈 뜨고 코 베인다"에서 "코심코심"("코 조심"을 반복한 말놀이)으로 바꾼다. 영문명 "Watch Your Nose"와 리포지토리명은 유지한다. `src/app/page.tsx` H1, `src/app/layout.tsx` `metadata.description`, `docs/PRD.md`, `README.md`의 해당 문구를 함께 갱신한다(완료된 phase의 `phases/0-mvp/step5.md` 등 기록물은 건드리지 않는다).
- 팔레트는 이미 코드(`globals.css`)에 반영돼 있는 라이트 크림 배경(`--background` `#fdf8f0`) + 번트오렌지 포인트(`--accent` `#e8623a`)를 정본으로 삼고, `docs/PRD.md`의 「디자인」 섹션을 이 현실(과거 "다크모드·블루" 표기)과 새 방향에 맞춰 개정한다. 브랜드 토큰 범위 내의 은은한 그라디언트·CSS 그레인·pulse·커서 반응 모션은 허용하되 보라색 글로우·블러·"AI 템플릿 티" 장식은 계속 지양하고 `prefers-reduced-motion`을 존중한다.
**이유**: 기존 랜딩이 "밋밋하다"는 팀 피드백. 유형을 사전에 노출하지 않는 제품 특성상(ADR-004) 랜딩이 가진 카드는 CTA 하나뿐이라, 첫인상은 마스코트·모션·카피 밀도로만 만들 수 있다. 표정 프레임을 쓰면 마스코트가 "코심코심"(코 조심을 반복하는 리듬)이라는 카피와 맞물려 커서에 반응해 코를 막는 인터랙션으로 서비스 톤을 즉시 전달한다. 상태 로직을 `src/lib/` 훅으로 빼는 것은 이 프로젝트의 로직/UI 분리 원칙과 TDD 가드(`tdd-guard.sh`) 구조에 맞고, CSS·`next/image`만으로 처리하면 ADR-002의 "외부 의존성 없음" 기조를 지킨다.
**트레이드오프**: 랜딩이 서버 컴포넌트 1개에서 "서버 셸 + 클라이언트 히어로 아일랜드"로 나뉜다 — ARCHITECTURE의 "랜딩은 Server Component로 유지 가능"은 셸에 한해 유효하고 히어로는 클라이언트다. 마스코트 이미지가 1장(PNG)에서 6장(WebP, 합계 목표 ~210KB)으로 늘고 첫 표정 전환 깜빡임을 막으려 마운트 시 전부 프리로드한다. 소스에 "웃는" 프레임이 없어 `safe`의 `relieved`는 "감은 눈" 프레임을 재사용한다 — "자는" 것처럼 읽힐 수 있고 개선하려면 아트 추가가 필요하다. `sad` 프레임은 원본에 발밑 그림자가 구워져 있어 스크립트로 하단 알파를 잘라내며, 잔여 헤일로가 남으면 `danger`→`surprised`로 폴백하고 5장으로 줄인다. 애셋 가공 스크립트는 스크래치패드에만 두고 산출물(WebP)만 커밋하므로 원본이 바뀌면 재가공은 수동이다(ADR-002의 "자동 동기화 파이프라인 없음"과 같은 선택). jsdom에 `window.matchMedia`가 없어 `tests/setup.ts`에 shim을 추가한다(reduced-motion 훅·인터랙티브 마스코트 테스트 공통 전제); 포인터 근접(`pointermove`) 반응은 jsdom `PointerEvent` 부분 지원 탓에 `onMouseEnter`/`onFocus` 경로로만 자동 커버하고 근접 로직은 수동 검증한다. 한글 웹폰트가 없어 커진 H1은 시스템 한글 폴백에 의존한다(`Noto_Sans_KR` 도입은 범위 밖 후속). 랜딩에 스크롤 섹션이 생겨 "한 화면"이 아니게 되지만 "진행 방식" 카피와 유형 비노출 원칙(ADR-004, `page.test.tsx`)은 그대로 지킨다 — 히어로의 떠다니는 카드 문구도 유형명·다음 단계를 드러내지 않는다.

### ADR-014: 보이스피싱 콘텐츠에 난이도 태깅 완료 + 실제 사례 기반 시나리오 4종 확장
**결정**: ADR-012에서 메커니즘만 넣고 미룬 보이스피싱 콘텐츠 난이도 태깅을 이번에 완료한다. 기존 시나리오 6개(`VOICE_PHISHING_SCENARIOS`)에 `difficulty`(`"easy" | "medium" | "hard"`)를 전부 부여하고, 실제 공개 자료(금융감독원 보이스피싱 지킴이·경찰청 사이버수사국·KISA·은행/카드사 공식 보도자료·신뢰할 수 있는 언론 보도)만 근거로 사례 뱅크(`docs/research/voice-phishing-case-bank/`)의 빈 카테고리 3종(납치협박형·메신저피싱형·택배배송사칭형)과 정상 통화 패턴 1건을 채운 뒤, 그 근거로 사기 시나리오 3개 + 정상 시나리오 1개를 추가한다. 최종 풀은 정상 4 + 사기 6 = 10개이며, easy/medium/hard 각 난이도에 정상·사기가 모두 1개 이상 존재하도록 배분해 `pickByDifficulty`가 난이도별로 의미 있는 부분집합에서 랜덤 선택하게 한다. 난이도 배정 기준은 `src/data/difficulty.ts`의 정의(easy=위험 신호가 뚜렷 / medium=여러 정보를 종합해야 판단 / hard=표면 인상과 실제 정답이 어긋남)를 따른다. 사례 뱅크 갱신·시나리오 작성은 `.claude/agents/`의 `voice-phishing-case-researcher` / `voice-phishing-scam-scenario-writer` / `voice-phishing-normal-scenario-writer` 가드레일을 그대로 준수한다(가해자 대사는 노드당 1~2문장, 실제 계좌번호·악성 앱 이름·피싱 URL·구체 범행 절차 재현 금지, 기관/상호명은 "OO은행"식 익명형만, 각 사례에 공개 출처 명시, 실제 대사 verbatim 금지 — ADR-005).
**이유**: ADR-012 트레이드오프에 명시된 "콘텐츠가 태깅될 때까지 난이도 선택이 실질 효과 없음"을 보이스피싱부터 해소한다. 보이스피싱은 선택지 기반 분기라 난이도 판정이 비교적 안정적이고, 사례 뱅크와 전용 에이전트 인프라가 이미 갖춰져 있어 실제 사례 기반 확장을 콘텐츠 안전 원칙을 지키며 할 수 있다.
**트레이드오프**: `src/data/voice-phishing.test.ts`의 하드코딩 카운트(6개 = 정상 3 + 사기 3)를 10개 = 정상 4 + 사기 6으로 갱신해야 한다. 케이스 조사·사기 판별 카드는 여전히 난이도 미태깅으로 남아 전체 풀 랜덤 fallback을 탄다(ADR-012 상태 유지). 난이도 배정값은 도메인 판단이라 팀 리뷰로 조정될 수 있다 — 이 ADR은 배분 구조(각 난이도에 정상·사기 공존)만 고정한다. 사례 뱅크가 늘어도 런타임 연동은 두지 않으며(ADR-002) 시나리오 반영은 수동이다.
