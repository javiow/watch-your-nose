# Step 0: docs-update

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 아키텍처와 설계 의도를 파악하라:

- `/CLAUDE.md`
- `/docs/PRD.md`
- `/docs/ARCHITECTURE.md`
- `/docs/ADR.md`

이 step은 코드를 전혀 건드리지 않는다. 뒤이은 step1(데이터/타입)·step2(캐릭터 설정 플로우)·step3(체험 컴포넌트 구현)이 참조할 설계 결정을 문서에 먼저 확정해 두는 것이 목적이다.

## 배경

팀원이 별도로 [`JUNGMyeong-jin96/HousingFraudDetect`](https://github.com/JUNGMyeong-jin96/HousingFraudDetect)라는 전세사기 위험 판별 웹게임을 만들었다. 캐릭터를 생성하고, 골목 맵을 걸어다니며 매물 5채에 들어가 등기부·전세가율 등 8개 서류 항목을 확인한 뒤 위험 여부를 O/X로 판정하고, 마지막에 결과 리포트를 보는 게임이다. 캐릭터/건물 스프라이트는 canvas 위에 절차적으로 그리는 픽셀아트라 외부 이미지·라이브러리 의존성이 없다.

이 게임을 현재 서비스의 3번째 체험 유형 "전세매물"(`typeId: "jeonse"`) 자리에 통째로 이식하기로 했다. 단, 원작 그대로는 아니고 이 프로젝트의 기존 원칙과 충돌하는 부분만 조정한다:

- **즉시 피드백 제거**: 원작은 매물 판정 직후 정답/해설을 바로 보여주지만, 이 앱은 "체험 중 정오답 노출 금지, 결과는 `/result`에서만 공개"가 이미 다른 두 유형(보이스피싱/사례선택)에 확정된 원칙이다. `jeonse`도 동일하게 적용한다.
- **유형명 비노출**: 기존 `experience-jeonse` step(`phases/0-mvp/step4.md`)의 금지사항에 "사용자 노출 텍스트에 유형명('전세매물')을 직접 쓰지 마라"가 이미 있다. 원작의 "전세사기 위험 점검 훈련 / JEONSE RISK FIELD TEST" 같은 리터럴 헤더 문구는 이식하지 않는다.
- **캐릭터 설정 유지 + 전역화**: 원작의 캐릭터 생성(나이대/직업/성별) 단계는 버리지 않되, `jeonse` 유형 전용이 아니라 랜딩 이후 전역 1회 단계(`/setup`)로 승격한다. 화면에는 노출하지 않고 세션에 저장만 하며, 향후 시나리오 매칭에 쓸 목적이다(매칭 로직 자체는 이번 범위 밖 — 지금 만들지 않는다).
- **5채→1건 집계**: 이 앱의 `ModuleResult`는 체험 유형당 1건이 원칙이므로, 매물 5채 판정을 하나의 `ModuleResult`로 집계한다.

## 작업

아래 3개 문서를 정확히 다음 내용으로 수정한다. 명시된 변경만 반영하라 — 이 문서들은 팀원 여러 명이 참조하는 합의된 설계 기록이다.

### 1. `docs/ADR.md`

기존 ADR-006 다음에 아래 2개 ADR을 순서대로 추가한다:

```markdown
### ADR-007: 전세매물 유형을 팀원 제작 "골목 이동 O/X 판정" 게임으로 교체
**결정**: 기존 2択 카드 선택형 전세매물 체험을 팀원 레포([HousingFraudDetect](https://github.com/JUNGMyeong-jin96/HousingFraudDetect))에서 이식한 게임으로 완전히 교체한다. 사용자는 골목 맵을 걸어다니며 매물 5채에 들어가 등기부·전세가율 등 8개 서류 항목을 확인하고 위험 여부를 O/X로 판정한다. 캐릭터/건물 스프라이트는 canvas 절차적 픽셀아트로, 외부 이미지·라이브러리 의존성이 없어 이식 비용이 낮다. `ExperienceModule<JeonseHouse[]>` 계약(하나의 `content`를 받아 `onComplete`로 `ModuleResult` 1건 반환)은 그대로 유지하고, 5채 판정을 하나의 `ModuleResult`로 집계한다(`score = 정답수/5*100`, 등급이 "safe"(80%↑)일 때만 `isCorrect: true`).
**이유**: 팀원이 이미 검증한 콘텐츠(매물 42개)와 게임플레이를 그대로 활용하고, 다른 두 유형 대비 몰입감 있는 체험을 제공한다.
**트레이드오프**: 원작의 "판정 직후 정답 공개" UX는 제거한다(이 앱의 "결과 페이지에서만 공개" 원칙 위반이므로) — 학습 임팩트는 다소 줄되 세 유형 전체의 일관성을 우선한다. 이동/스프라이트가 추가되며 세 체험 유형 간 인터랙션 복잡도 격차가 커진다(ADR-006에서 이미 허용한 비일관성의 연장). 세션당 판정 항목이 1개→5개로 늘어 이 유형만 완료 시간이 눈에 띄게 길어진다.

### ADR-008: 캐릭터 설정(나이대/직업/성별)을 랜딩 이후 전역 1회 단계로 추가
**결정**: `/` 랜딩과 `/session` 사이에 `/setup` 단계를 신설해 나이대·직업·성별을 한 번 수집하고 `SessionProvider`의 `playerInfo`에 저장한다. 화면에는 노출하지 않고 향후 시나리오 매칭(콘텐츠 추천/난이도 조정 등)에 쓸 목적으로 보관만 한다 — 매칭 로직 자체는 이번 범위 밖. "다시 체험하기" 재시작은 `/setup`을 다시 거치지 않는다(`resetSession()`이 `playerInfo`는 건드리지 않음).
**이유**: 팀원 게임의 캐릭터 생성 단계를 버리지 않고 전역 자산으로 승격해 향후 개인화 기능의 기반을 마련한다.
**트레이드오프**: 랜딩→세션 사이에 화면이 하나 늘어난다. 지금은 수집한 정보를 아무 데도 쓰지 않는다(향후 매칭 기능 전까지는 순수 수집 단계).
```

### 2. `docs/PRD.md`

- "핵심 기능" 절에서 기존 §2("3개 체험 유형(보이스피싱 / 사례선택 / 전세매물)을 매 세션...") 앞에 새 항목을 삽입하고, 이후 기존 항목 번호를 모두 하나씩 민다:

- (번호가 밀린 뒤) "전세매물" 항목을 아래로 교체:
  `전세매물 — 골목 맵을 이동하며 매물 5채를 방문해 등기부·전세가율 등 8개 서류 항목을 확인하고 위험 여부를 O/X로 판정한다. 판정 직후에는 정답을 알려주지 않으며(다른 유형과 동일한 원칙), 5채 판정을 종합해 하나의 성적으로 채점한다.`

### 3. `docs/ARCHITECTURE.md`

- 디렉토리 구조 코드블록을 아래처럼 갱신한다(주석 문구 위주 변경, 실제 트리는 이후 step에서 만들어짐):
  - `app/` 아래에 `setup/page.tsx` 줄 추가: `# 캐릭터 설정(나이대/직업/성별), 랜딩 이후 1회성 전역 단계`
  - `components/experiences/` 설명을 `VoicePhishingExperience(+ChatBubble/TypingIndicator/ChatChoiceButtons), CaseSelectExperience, JeonseExperience(+jeonse/ 하위: MapBoard/HouseDialogPanel/HouseSprite/PlayerSprite/sprites/boardConfig)`로 갱신
  - `types/` 설명에 `JeonseHouse`를 추가하고(`ListingPair` 대체), `types/player.ts`(`PlayerInfo`) 줄 추가
  - `data/jeonse.ts` 옆 설명을 `# 매물 42종 + 5채씩 정적 분할한 세트`로 갱신
- "데이터 흐름" 블록의 첫 줄과 두 번째 줄 사이에 삽입:
  ```
  → "/setup": 나이대/직업/성별 선택 (1회, 화면 미노출 저장 — SessionProvider.playerInfo)
  ```
  그리고 마지막 줄("다시 체험하기 → 세션 재초기화 → 랜딩을 거치지 않고 바로 "/session"")을 아래로 교체:
  `→ "다시 체험하기" → 세션 재초기화 → 랜딩·설정 화면 모두 건너뛰고 바로 "/session"`
- "상태 관리" 절 첫 문장 뒤에 이어서 추가: `세션에는 `playerInfo: PlayerInfo | null` 필드도 함께 보관한다 — 캐릭터 설정 화면에서 한 번 저장되면 `resetSession()`으로도 초기화되지 않는다.`
- "엣지 케이스 / 방어 로직" 절에 아래 항목들을 추가:
  - `/session`은 `playerInfo`가 없으면(직접 URL 진입 등) `/`로 리다이렉트한다 — 기존 빈 세션 리다이렉트와 동일한 패턴.
  - 전세매물은 5채 판정을 하나의 `ModuleResult`로 집계한다 — `score`는 정답수/5*100, `isCorrect`는 등급이 "safe"(80%↑)일 때만 true, 그 외에는 `mistakeTag: "missed-lease-fraud-signal"`.
  - 전세매물 진행 중에는 헤더 카운터·맵 위 집 배지·사이드바 점검기록 배지 어디에도 정오답을 노출하지 않는다 — "완료/미점검" 여부만 표시한다(즉시 피드백 금지 원칙의 연장).

## 금지사항

- `src/` 이하 코드 파일을 이 step에서 수정하지 마라. 이유: 이 step은 문서 전용 — 코드는 step1/2/3에서 다룬다.
- 위에 명시되지 않은 다른 문서 섹션(예: PRD의 디자인 절, ADR의 철학 절)을 임의로 고치지 마라. 이유: 이번 변경과 무관한 합의 사항까지 건드리지 않기 위함.
- 기존 테스트를 깨뜨리지 마라.
